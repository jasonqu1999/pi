## 分析范围

对象为 `pi/` 的 v1.0.2，已核验提交为 `cd32f7725fdbddbaecdff5b1e68491563394e0ca`，执行前复核。覆盖全仓源码及仓库内相关文档、测试、示例；排除依赖、构建产物与既有分析输出，记录覆盖缺口。

全仓概览说明各包的职责、接口、依赖和边界。以终端交互为主入口，启动、配置与模式分流追到会话及 Agent 创建；输入追到会话层；输出追到事件消费者。终端渲染、布局、按键等界面内部实现不深入。

核心主链深入追踪：

- 会话与 Agent 如何连接，用户消息如何进入上下文。
- 上下文如何变换并交给模型层，流式响应如何形成消息和工具调用。
- 工具如何查找、校验、调度与执行，结果如何回填，何时发起下一次请求。
- 正常停止、工具报错、模型报错和取消分别走哪些出口；区分低层循环结束与会话最终结束。
- 原始会话记录、Agent 内存状态与模型请求上下文分别由谁管理，事件通知和会话记录如何随过程更新。

控制流要画出循环、条件分支与事件订阅关系；数据流要说明消息和状态的变化。会话记录更新按实际触发点解释，不能统一画成最终回答之后的一个步骤。

以“新会话请求总结一个小 Markdown 文件，模型返回 read 调用，再根据结果回答”为正常静态走读例子，并对照文件不存在时的错误路径。这里的模型输出是推演前提，不代表真实模型一定选择该工具；不执行该任务。每一步说明输入、执行者、条件、输出、状态归属及对应文件与符号。

局部源码深入到能解释上述变化并判断相邻修改的影响。核对 1.0.2 的工具声明、编排及包边界，避免沿用旧版结论。供应商边界说明 Pi 如何交出上下文和接回结果；各供应商的协议细节保留入口。

上下文压缩、消息插队/跟进（steering/follow-up）、自动重试与恢复、扩展拦截等支线，本轮只说明职责、触发条件、状态归属、接入位置和后续问题；具体算法与完整分支后续再详细分析。主链遇到这些机制时标出连接，不把支线展开作为主链完成的前提。命令审批仅作为未来功能的候选接入方向。

学习入口先给问题、预测任务和必要导航；完整解释单独链接，供预测和源码核对后查阅。Markdown 与 Obsidian 均采用这一组织方式。
